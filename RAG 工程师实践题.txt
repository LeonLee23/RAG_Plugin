RAG 工程师实践题：通用知识库系统DEMO

1. 任务目标
   实现一个通用 RAG 知识库系统DEMO，完成“创建知识库 → 上传文档 → 解析与索引 → 检索 → 基于证据回答”的完整流程。
   系统以 Server 形式运行，提供简单的 Web 管理页面，支持通过 Claude Code （或 Codex）使用提供的 Skill 和 MCP 使用知识库。
   本题重点考察 RAG 原理、工程设计、效果验证，以及使用 AI 编程 Agent 交付可靠软件的能力。前端美观程度不作为主要评价依据。
2. 技术约束
   编程语言不限。
   不使用 LangChain、LangGraph 等 RAG / Agent 编排框架。允许使用其他基础组件和SDK。
   可以参考 RAGFlow、WeKnora 的设计，但不能通过直接部署、包装现成 RAG 产品完成本题。可以使用其中的功能模块，但是需要在设计文档中说明。
3. AI Agent 协作要求
   要求使用 AI 编程 Agent 辅助完成开发，工具不限。
   项目根目录必须提供 AGENTS.md，至少说明项目结构、模块边界、开发约束、运行与测试命令，以及 Agent 应遵循的工作方式。使用的工具如需其他入口文件，应确保它能读取这些约束。
   需要理解并能够解释 AI 提交的内容。
4. 部署与 Web 管理
   使用 Docker Compose 部署。提供 .env.example 和明确的启动步骤；填写模型 API 配置后，应能按文档启动全部必要服务。
   Web 页面至少支持创建、查看和删除知识库，上传、查看和删除文档。
5. 文档处理
   支持带可提取文本的 PDF 和 .docx，包括其中的内嵌图片；不要求支持扫描件 OCR、手写内容或旧版 .doc。
   文本与图片都应进入可检索链路。图片可以通过多模态模型生成描述、提取信息或采用其他方案，但需要保留它与原文档、所在位置的对应关系。
   分块与索引方案自行设计，说明如何处理标题、段落、图片上下文和来源定位。复杂表格、公式和版式还原不作强制要求。
   LLM、Embedding 和多模态能力可以使用 API 服务，无需本地部署模型。
6. 检索与回答
   必须实现三种可实际调用的召回方式：向量召回、关键词召回和图谱召回。
   图谱召回至少需要完成“从文档提取实体与关系 → 持久化 → 利用关系检索 → 返回原文证据”的最小闭环。仅展示关系图，或只让模型生成实体列表，不算完成。图存储方案不限。
   支持分别使用三种召回方式，并至少实现一种融合检索方案。是否使用重排序，由候选人自行决定并解释。
   检索必须限定在指定知识库内。返回结果应包含来源、原文片段及必要的召回信息，便于排查效果问题。
   基于检索结果生成的回答应引用来源；通过 Claude Code （或 Codex）演示。
7. Claude Code 接入
   提供可用的 MCP Server 和配套 Skill，使 Claude Code 能够发现知识库、检索内容，并基于检索证据回答问题。
   MCP 至少提供知识库列表和知识库检索工具；Skill 负责说明何时调用、如何选择知识库、如何引用证据，以及无结果时如何处理。
   提供安装配置和完整演示示例。MCP 应调用 Server 的统一业务能力，避免另写一套检索实现。
8. 工程质量
   项目目录清晰，模块职责、依赖方向和数据流明确。文档处理、索引、检索、回答与协议接入应有合理边界，避免将核心逻辑集中在接口或页面中，做好系统分层和功能模块化。
   注释重点解释设计原因、边界条件与取舍。
   至少覆盖核心流程，以及知识库隔离、处理失败、删除后不可召回等关键边界测试。
   项目提供必要的架构与设计文档、设计文档，说明选型、模块职责、数据流、处理与检索策略、已知限制、扩展等，候选人需要理解并能够解释它们。
9. 验收
   提交到个人 Github 个人项目上，README说明下使用方法。
   准备测试数据进行简单演示。
10. 加分项
  提供 Benchmark 与优化分析 方案和工具，不要求 Web 页面，提供脚本 or 工具即可（要有文档说明）。
  根据自己的理解提出新功能或架构改进，提供设计文档，标注为“待实现”即可，说明解决的问题、收益、代价和验证方式，无需编码实现。

参考项目：RAGFlow、WeKnora。
